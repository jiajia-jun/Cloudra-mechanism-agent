写作口径：标题是本页要回答的问题；正文是可直接上屏的文字；讲述说明供演讲者备注使用。每页“实现依据”是内部技术出处，不等于公开论文或独立实证。

## 1｜可靠运行：研究过程能被追溯和恢复

**归属：创新二——把常规运行负担交给系统**

**上屏正文**

- 一个机理任务会跨越多轮对话和多次耗时计算；系统必须知道“已经做过什么、还欠什么”。
- Cloudra 将关键状态变化记录为事件：先保存，再更新任务状态，最后执行外部动作。
- 判断规则尽量写成可重复检验的函数；重启后可根据记录恢复研究进度。
- 自动测试覆盖事件重放、恢复和状态约束；CI 设置代码覆盖率门槛。

**讲述说明**：这里的“函数式”是把同样输入对应同样结果的判断逻辑从网络请求、数据库写入中分开；“事件”是可追溯的状态变化记录。不要说所有外部动作都能重放，也不要把 CI 的 65% 下限说成当前实测覆盖率。

**实现依据**：`cloudra/runtime_v2/commands.py`、`events.py`、`apply.py`；`tests/test_runtime_v2_replay_equivalence.py`；`.github/workflows/ci.yml`。

## 2｜AgentHub：让专长不同的 Agent 直接协作

**归属：创新一的知识支持；创新二的协作基础**

**上屏正文**

- AgentHub 相当于研究组的讨论区：成员可以公开发现、提出问题，也可以直接请另一位专长 Agent 帮忙。
- 帖子与消息留下记录；新加入的 Agent 有独立任务和生命周期。
- 同一入口还能检索带来源的化学知识，区分论文信息、已核实计算与模型假设。
- 这种设计减少固定“总指挥”逐项转述的负担；科学结论仍需计算证据检验。

**讲述说明**：所谓“去中心化”限定在 Agent 间发起协作与共享信息，不代表没有统一存储、调度或监督。知识检索为判断提供候选线索，不能直接充当计算证据。图谱、语义与模糊检索的实现细节可留在问答。

**实现依据**：`cloudra/runtime_v2/hub_bridge.py`、`knowledge.py`；`cloudra/knowledge/plugin.py`；`tests/test_hub_api.py`、`tests/test_runtime_v2_knowledge.py`。

## 3｜化学工具：覆盖从分子表示到结果解释

**归属：创新一——为 Agent 提供可选择、可检查的候选**

**上屏正文**

| 研究问题 | Cloudra 提供的能力 | 代表工具 |
| --- | --- | --- |
| 研究的是哪个分子、哪些原子在变化？ | 名称与结构转换、原子对应、反应中心识别 | `name_to_structure`、`reaction_mapping` |
| 分子可能怎样摆放和反应？ | 构象搜索、反应假设、过渡态初猜 | `conformer_search`、`mechanism_predict`、`ts_guess` |
| 候选能否被实际计算？ | 量化输入、任务提交与运行状态查询 | `qm_input_writer`、`submit_compute_job` |
| 结果支持什么结论？ | 日志解析、电子结构与热化学分析 | `log_parser`、`electronic_analysis`、`thermo_analysis` |

**讲述说明**：“构象”是同一分子不同的空间摆法；“过渡态”是反应跨越能量障碍时的关键结构。FlowER 的反应预测只生成假设；计算程序正常结束也不能单独证明假设成立。工具覆盖广度不等于每类化学反应都已完成验证。其余工具列于备份页。

**实现依据**：`cloudra/tools/registry.py` 及 `cloudra/tools/Chemtool/`。

## 4｜工作流：程序推进常规步骤，Agent 处理科学断点

**归属：创新二——把执行负担从 Agent 移出**

**上屏正文**

1. Agent 明确研究目标、反应物与候选路径，并作方法选择。
2. 工作流建结构、准备输入、提交计算、等待结果并解析输出。
3. 程序检查结果是否满足预先声明的条件；需要计算时继续推进。
4. 遇到原子对应错误、结构不合理或候选失败等断点，才把具体问题交还 Agent 判断。

**页末句**：Agent 负责“下一步研究什么”；系统负责“已决定的步骤可靠地做完”。

**讲述说明**：以过渡态搜索流程为例，`ts_prepare` 启动，`ts_resume` 在阻塞处继续；工具会指出需要修正的声明，而不是让模型反复查询进度。该流程不能保证任何反应都找到真实过渡态。实际计算引擎及可选依赖需安装配置。

**实现依据**：`cloudra/tools/Chemtool/ts_search_process.py`、`cloudra/tools/core/ts_process.py`、`cloudra/scheduler/`。

## 5｜机理证据图：把“算过”与“证实”分开

**归属：创新三——可核查的机理交付，核心科学贡献**

**上屏正文**

- 图中的节点是反应物、中间体和产物；连线是提出的反应步骤。
- 每个需要证实的结构或步骤，都附有应完成的计算及其结果。
- 系统从已完成的计算文件提取证据，检查结构、振动、路径等条件；缺口继续保留。
- 最终是否完成，取决于证据覆盖情况，而非 Agent 的文字声明。

**页末句**：一份“机理答案”，必须同时给出路径和支持每一步的材料。

**讲述说明**：DAG 是承载交付与阶段要求的图，不是聊天流程图。对于默认机理草稿，过渡态优化与频率分析是必要阶段；IRC 可在需要路径证明时写入契约，不应口头说“每条边都强制跑完整 IRC”。系统给出的是基于既定规则的证据判定，不是绝对科学真理。

**实现依据**：`cloudra/dag/models.py`、`completion.py`、`evidence_ingest.py`、`controller.py`；`tests/test_dag_completion.py`。

## 6｜记忆：保留可复用经验，但不把经验当证据

**归属：创新二的辅助能力**

**上屏正文**

- Agent 可以把通用的操作经验和失败教训写入长期记忆，供以后任务参考。
- 记忆会跨任务加载，内容过长时压缩并归档原文。
- 项目专属路径、编号等不应混入全局记忆；写入前有范围检查。
- 记忆只影响“下次优先尝试什么”，不能把未经核实的经验升级为科学结论。

**讲述说明**：CatDT 对相关能力使用“自迭代”等表述。Cloudra 当前实现的是可控、可追溯的经验复用；没有建立“计算结果自动进入知识图谱、经独立核验后反过来改善策略”的完整闭环。不要宣称已经自我进化。

**实现依据**：`cloudra/persistence/memory.py`、`cloudra/tools/Writetool/update_memory.py`、`cloudra/tools/core/memory_scope_guard.py`；`tests/test_memory_scope_guard.py`。

## 7｜Benchmark：用不同困难检验科学判断

**归属：创新四——独立评价方法**

**上屏正文**

| 题目层级 | 主要考什么 |
| --- | --- |
| 基础题 | 能否给出自洽的结构和反应步骤？ |
| 复杂题 | 能否组织多步机理与竞争路径？ |
| 立体选择题 | 能否区分空间摆法不同的竞争反应？ |
| 方法边界题 | 当现有方法不能可靠计算时，能否标出不可达部分？ |

**页末句**：这套考卷检查“选对问题、取得证据、承认方法边界”三个能力。

**讲述说明**：当前仓库有四档题目文件，但题集仍在建设；不要使用旧论文草稿中的“已完成 100 题”。方法边界题要求提交机理图并将确实不可达的部分标为 `accessible=false`，不是简单拒答。层级名称是能力轴，不保证每个题目都已有独立核实的高质量参考结果。

**实现依据**：`cloudra/benchmark/schema.py`、`gen_*_tasks.py`、`ideapool/tasks/`。

## 8｜Benchmark 评分：只看交付物，不看解释得多漂亮

**归属：创新四——独立评价方法**

**上屏正文**

- **机理覆盖**：提出的物种和反应步骤，是否对应参考机理？
- **证据自洽**：稳定结构、过渡态和路径，是否有相应计算文件支持？
- **结果准确**：关键能垒、性质或选择性，是否与参考答案相符？
- 评分读取交付图与计算日志，不读取 Agent 的结论性文字；每次运行保留独立记录。

**讲述说明**：现行实现的三部分权重为 0.1、0.3、0.6；缺证据、声明与日志矛盾等情形有明确处理。这里介绍的是评价协议，不能从协议本身推出 Cloudra 已获得高分。下一阶段需要发布经复核的题目、同题基线和重复实验结果。

**实现依据**：`cloudra/benchmark/runner.py`、`graph_similarity.py`、`selfconsistency.py`、`accuracy.py`；`tests/test_benchmark.py`。

## 9｜当前边界与通用化学框架的条件

**归属：四项创新的研究计划与边界**

**上屏正文**

**已经建成的基础**：可恢复运行、多 Agent 协作、化学工具链、机理证据图和独立评分器。

**仍需完成的验证**：扩大并复核参考题；在轴手性等真实任务上报告成功率、计算成本和失败原因；与已有系统做同题比较与模块消融。

**通用框架的判断标准**：换一种反应或计算引擎，仍能沿用任务管理与证据规则，并说明哪些科学规则必须重新制定。

**页末句**：可扩展架构提供了可能性；跨体系实证才能证明“通用”。

**讲述说明**：这页自然转入轴手性案例：它既有真实化学价值，也把三维候选、智能选择和证据核查同时推到困难区域。不要声称现阶段已经覆盖所有有机反应、所有计算方法，或已优于 CatDT/ARCHE。

**实现依据**：上述模块；轴手性研究基础与项目计划。此页的后半部分是研究计划，而非完成结果。

## 备份页｜化学工具覆盖清单

| 研究环节 | 已注册的代表工具 | 回答的化学问题 |
| --- | --- | --- |
| 输入与分子表示 | `name_to_structure`、`image_to_smiles`、`smiles_to_mol`、`format_converter`、`cdxml_to_graph` | 把名称、图片或常见结构文件转成可计算、可追踪的分子表示 |
| 结构展示 | `molecule_drawer`、`pymol_render` | 检查二维连接与三维形状，帮助人阅读结果 |
| 反应识别 | `reaction_mapping`、`internal_coordinates` | 对应反应前后原子，识别成键、断键及关键距离和角度 |
| 候选生成 | `conformer_search`、`mechanism_predict`、`ts_guess` | 搜索空间姿态、提出反应假设、生成并筛查过渡态初猜；预测不是计算证据 |
| 过渡态流程 | `ts_prepare`、`ts_resume` | 推进一条过渡态搜索流程，在科学断点处请求修正 |
| 量化计算 | `qm_input_writer`、`submit_compute_job`、`query_compute_job`、`query_compute_queue` | 准备输入、提交作业、查看运行与资源状态 |
| 计算解释 | `log_parser`、`electronic_analysis`、`thermo_analysis` | 从日志检查结构、电子性质、能量与热力学结果 |
| 实验资料处理 | `ir_processor`、`nmr_processor` | 整理红外和核磁谱图；不是机理计算本身 |

这张表是功能覆盖，不表示每个工具都已在同一套真实任务上完成端到端评测。外部引擎与可选依赖的可用性取决于安装环境。
